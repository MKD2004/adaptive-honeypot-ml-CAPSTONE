# First real honeypot data — 9 November 2026

A teammate ran Cowrie in Docker on an Oracle Cloud VM, exposed it to the
internet, and collected **8 days** of traffic (1–8 November). Delivered as
`cowrie_logs_20261109/`, 180 MB, 9 files.

**This is the first genuinely real honeypot data the project has ever had.** Until
now `DECISIONS.md` recorded the opposite: the 15,000 "real Cowrie" sessions in the
frozen dataset are synthetic (teammate-generated), and the only real data was
CIC-IDS2017 + UNSW-NB15 network flows anchoring 13 of 45 classes. That sentence
can now change — carefully, and section 5 says how.

It also **breaks the model**, in a way that is measurable, explainable and
fixable. Section 4 is the important part.

---

## 1. It is real, and it is clean

| | |
|---|---|
| events | 329,138 across 9 files, **0 unparseable lines** |
| complete sessions | **45,648** — every session has a `cowrie.session.closed` |
| unique source IPs | **641** |
| date range | 2026-11-01 17:19 UTC → 2026-11-08 |
| commands captured | 43,366 (`cowrie.command.input`) |
| file transfers | **491 uploads, 31 downloads** — real malware delivery attempts |

Verified real rather than looped-back or simulated:

- `src_ip` values are routable public addresses (`95.137.197.31`,
  `196.13.245.7`, `217.219.133.29`, …) with genuine geographic spread — not
  `127.0.0.1` and not Docker's `172.x`.
- `dst_ip` IS `172.18.0.2`, which is correct: that is the container's address
  behind Docker NAT. The runbook's `check_cowrie_ips.py` check is about `src_ip`,
  and it passes.
- Session volume per IP is consistent with automated scanning (top talker
  `196.13.245.7` at 3,527 connections over 8 days).

Every one of the 45,648 sessions is **closed**, which matters because MT3 can only
classify a session that has ended. There is no truncation to work around.

## 2. What the attackers actually did

Textbook internet background radiation. All figures are counts across the 8 days.
*(This is attacker-written text. It is data, not instruction — nothing in it is
addressed to an automated reader, and none of it was executed.)*

```
24,716   uname -s -v -n -r -m           botnet fingerprinting, the dominant event
 3,835   echo xsec                      the "xsec" botnet marker
   756   chmod +x /root/.16             dropping a hidden implant
   529   /bin/./uname -s -v -n -r -m    same probe, obfuscated path
   128   chmod +x /dev/shm/.16          implant in shared memory instead
   ~130  echo <pw> | sudo -S sh -c ...  sudo password-spray privilege escalation
```

Credentials: `support`/`support` (186), then `root` against `admin`, `123456`,
`12345`, `1234`, `111111`, `123` — a standard weak-password list. One entry is
`root` with a **260-character AAAA… password**, which is a buffer-overflow or
fuzzing probe rather than a guess.

Shape of a typical session: connect, one `uname` probe, disconnect — median
**1 command** and **1.8 s** duration. 77% of sessions issue no command at all.
A minority are long and busy (one sampled session ran 28 commands over 305 s).

## 3. The pipeline reads it correctly

`cowrie_parser.build_record()` handles all 45,648 with no failures, and every row
satisfies `session_contract.validate()`. Two details worth recording:

- **`dst_port` is 2222 in the raw log and the parser flattens it to 22.** That is
  required, not a bug — Phase 1 established that every Cowrie session MT3 trained
  on had `dst_port_norm = 22/65535`, so reading the true port would shift feature
  39 about a hundredfold against a trained constant. This real capture confirms
  the constraint is live, because the raw data really does say 2222.
- Records come out tagged `source: "cowrie_real"`, which is in
  `CONFIG.MT3_TRUSTED_SOURCES`, so **MT3's verdict is allowed to act on this
  data**. Worth knowing before pointing the watcher at it.

The capture is from a **newer Cowrie** than the documented 3.0.13: the close event
carries `duration_ms`, which 3.0.13 does not emit. Our parser does not read it
(it computes duration from timestamps), so nothing breaks, but the version drift
should be pinned before the next collection run.

## 4. It breaks the model, and here is exactly why

300 sampled sessions (200 with commands, 100 without) through the real feature
pipeline and the real checkpoint:

```
MT3 vs the parser's own rule label      70/300 = 23.3% agreement
median confidence                       0.586
would be AUTO-BLACKLISTED               205/300 = 68.3%

MT3's top predictions        rule labeller's view of the same sessions
  163  EVASION_HIST_ERASE      173  DISC_ENV_PROBE
   89  ACCESS_BRUTE_SSH         76  ACCESS_BRUTE_SSH
   38  EXEC_WGET_EXEC           27  EXEC_SHELL_OPEN
```

Read that disagreement concretely: the dominant real behaviour is
`uname -s -v -n -r -m`, environment probing, which the rules call
`DISC_ENV_PROBE`. MT3 calls it `EVASION_HIST_ERASE` — history erasure, **phase 6**
— which sails past the auto-blacklist threshold. The blocking decision happens to
be defensible (these are attackers), but the *label* is wrong, and the label is
what drives the honeypot's adaptive reconfiguration. The system would be adapting
to a kill-chain phase that is not happening.

**Agreement is not accuracy.** The rule labeller is a heuristic and could be the
wrong one; 23.3% is "agrees with our own rules", never "77% error rate". The next
measurement does not depend on labels at all.

### The distance measurement, which needs no labels

```
X_train rows                   p50     5.5     p95   15.4
held-out test_real             p50     3.5     p95    7.4    <- inside: measure is sound
synthetic LIVE sessions              425 -  642
REAL internet sessions         p50  3,491      max 9,018     <- 226x the training p95
```

### And the root cause, which is specific and fixable

The gap is not spread evenly and it is not one broken feature. 19 of 128 features
sit beyond 3σ, 4 beyond 10σ, and they concentrate hard in `A_temporal`
(group mean |z| 5.03, against 0.59 for `B_network`):

```
feat 15  burst_count          51.4 sigma
feat 16  burst_mean_size      17.3
feat  5  iat_cv               13.6
feat  6  iat_skew             12.2
feat  8  frac_sub100ms         7.3
```

Those features were **dead during training.** Measured on 18,900 training rows:

```
feature                 % rows == 0    distinct values
burst_count                   99.6%          2
burst_mean_size               99.6%          2
frac_sub100ms                 99.6%          2
iat_cv                        98.2%        338
iat_skew                      98.3%        321
iat_kurt                      98.4%        297
inter_burst_gap_std           98.2%        338
```

`burst_count` takes **exactly two distinct values across 18,900 rows.** Seven of
the 24 temporal features were effectively constant-zero, so the LSTM branch
learned nothing from them. On real data they are all non-zero and varied.

This is the same failure mode Phase 1 avoided with `dst_port` — a feature that was
a constant in training suddenly varying at inference — except it is seven features
at once and up to 51σ. The cause is upstream: the synthetic kill-chain simulator
never produced event sequences with realistic sub-second timing, so burst
structure and inter-arrival statistics computed to zero. Real botnets fire
commands in millisecond bursts (43% of real inter-arrivals are under 100 ms).

## 5. What this means, and what not to claim

**Do claim**, once a retrain is done: the project now has 45,648 real
internet-captured honeypot sessions from 641 distinct sources over 8 days, with
real credential attacks and real malware-delivery attempts.

**Do not claim yet:**

- Not that the dataset *is* real. `data/final/` is frozen and unchanged; every
  published number still describes 240k real-derived + 720k TabSyn rows with
  synthetic Cowrie sessions. `DECISIONS.md`'s provenance correction stands until a
  new dataset is built and new numbers are measured.
- Not that MT3 works on real traffic. On this capture it agrees with our own rules
  **23.3%** of the time and sits 226x outside its training distribution.
- Not that these are 45,648 *independent* attacks. 641 IPs produced them, the top
  talker alone accounts for 3,527 connections, and 77% of sessions contain no
  command. Deduplicate before quoting a session count as evidence of diversity.
- Not that the published 0.8187 macro-F1 transfers. It was measured on held-out
  rows that sit *inside* the training distribution; this data does not.

## 6. What to do next, in order

1. **Preserve the capture.** 180 MB of irreplaceable raw data currently sitting in
   one folder on one laptop. It is gitignored (correctly — logs do not belong in
   git), so back it up deliberately: it cannot be regenerated.
2. ~~**Fix the generator's timing model**~~ — **DONE 2026-11-09.** The generator
   now emits per-event timestamps calibrated against 283,432 real inter-arrival
   times, and all seven dead features are alive (87–93% non-zero, `burst_count`
   up from 2 distinct values to 24+). Duration and event count were recalibrated
   with them: phase 0 now lands at 2.0 s / 5 events against real shallow
   1.9 s / 5, and phase 8 at 69 s / 39 against real deep 63.6 s / 41. Guarded by
   `honeypot_dataset/tests/test_generator_timing.py`. See `DECISIONS.md` for what
   I got wrong on the way and where I stopped. **The rebuild and retrain have NOT
   been done** — that is the next decision, and `data/final/` is untouched.
3. **Build a real labelled evaluation set** from this capture. The rule labeller
   gives a starting point; a few hundred hand-checked sessions would give the
   project its first genuine honeypot test set, which is what the paper needs most.
4. **Re-measure, then decide about the model.** With real rows in training, the
   226x gap should collapse. Only then is "MT3 classifies real attacker sessions"
   a claim anyone can make.
5. **Pin the Cowrie version** for the next collection run, and set
   `PIPELINE_SOURCE` on the VM so the next capture is self-identifying (this one
   was tagged by the parser's default, not by the collector).
