## 1. The one-paragraph version

The system went from "one honeypot, hardcoded" to "a pipeline that can take
several honeypots, with the model on a leash wherever it has not earned trust."
Along the way, four security findings from the 2 November review were closed or
mitigated, a 9-commit branch was merged, and the deployment kit was audited before
anyone tries to use it. Nothing was deployed to a public server — that still needs
a VPS.

The recurring theme, and the most useful thing to take away: **MT3 is confident
when it is wrong**, so every guard built this session is a structural one (does
this verdict come from a source we trained on? does a second signal agree?) rather
than a confidence threshold. Thresholds were tried and measured to fail, twice.

## 2. Day one — 3 November

### The demo, and a 20-second bug

The two-laptop demo was run end to end. A teammate's `ssh` kept dying with
`Connection closed by <host>`, which reads like a firewall problem and is not one:
`demo/real_server.py` gave a client **20 seconds** from SSH handshake to finishing
authentication. Fine for `attack_client.py`, which does it in milliseconds;
impossible for a person clearing the host-key prompt and then typing a password.
Raised to 120 s (`156c82d`).

Diagnosis evidence: the session showed a complete key exchange (1,845 bytes in,
1,813 out, 30.8 s) and **zero** auth events ever reaching the server, because
`transport.accept()` had already given up.

### DEMORUN.md was wrong about the act order

Its documented sequence could not work on a clean reset, and this is worth
understanding because it is a property of the design, not a bug:

The gateway scores a connection **at connect time**, before any command exists.
A clean `127.0.0.1` fires no signals at all — score 0.14 against a 0.45 threshold
— so it is routed to the *real server*, where the attack is refused for bad
credentials and the honeypot captures nothing.

So a benign act and an attack act need **opposite reputations from the same IP**,
and reputation is per-IP:

| state | benign act | deep attack |
|---|---|---|
| clean | ✅ real server | ❌ real server, auth refused |
| blacklisted | ❌ honeypot | ✅ honeypot |

Fix: put `brute_force.py --flood 0` second. Its 12-connection pre-burst is what
trips the behaviour signal, and dropping the flood keeps it to 18 connections,
under the 20/min rate limit, so acts 3-5 can still connect. `DEMORUN.md` now
documents five acts in that order, each with the output it actually produced.

### MULTI_HONEYPOT.md

Written as the plan for growing past one honeypot (`2964d53`). Decisions recorded:

## 3. Day two — 4 November

### Phase 1: the pipeline can read more than one honeypot

`cowrie_parser.build_record()` stamped every session `dst_port=22
protocol="ssh"`, so the function that decides which honeypot a session belongs to
could only ever answer `SSH_HONEYPOT`. The whole port→honeypot table was dead
code.

**The obvious fix was wrong, and this is the most important paragraph in this
document.** Reading the real port from the log would have broken the model
silently:

```
raw cowrie.json dst_ports:  {2222: 39931, 22: 19, 3306: 21, 443: 17, 80: 13}
what build_record emitted:  22, for every session, always
```

Every Cowrie session MT3 trained on therefore had `dst_port_norm = 22/65535 =
0.000336`. Reading the real port makes live sessions report 2222 → 0.0339, a
**~100x shift** in feature 39 against a value the model has only ever seen as a
constant. It raises nothing. It just mispredicts.

So `protocol` and `dst_port` became keyword parameters whose **defaults reproduce
the old behaviour byte-for-byte**. Notebook 01 calls it with no keywords, so the
frozen dataset is unaffected; a new parser passes its own values.

Also in `7cf0030`:

- `session_contract.py` — the ~22-key dict every parser must emit, written down
  and **enforced by tests**, with negative controls. The extractors call
  `session.get(key, default)` everywhere, so a missing key does not crash; it
  silently becomes a default and one of the 128 features goes quietly wrong.
- `LogSource` — the watcher now takes N sources instead of one hardcoded
  `cowrie.json*` glob.
- `PIPELINE_SOURCE` and `sensor` on every result, ported by hand from a teammate's
  commit (cherry-picking would have added a test importing a module that is not
  on `main`).

### Phase 1b: the text features, settled by measurement

A worry turned out to be misplaced, and a decision turned out to be easy once
measured.

**The worry.** `ACCESS_BRUTE_HTTP` scoring a perfect F1 on 121 rows looked like
train/test leakage. It is not: that class is **95.9% clean** (116 of 121 rows),
and MT3 gets **116/116** right. The real caveat is different — those rows are
CIC-IDS2017 *network flows*, not honeypot captures, so the result says nothing
about live HTTP traffic.

**The decision.** Group D (30 of the 128 features) is a language model fitted on
*shell commands*. What should a web or auth honeypot feed it?

```
text domain                   variance the 30 shell-fitted axes keep
shell commands (in-domain)    90.8%
HTTP request lines            73.6%
SQL injection payloads        64.1%
credential pairs              71.4%
```

Feeding it foreign text destroys a third of the signal. But the deciding number is
where a **zero-fill** lands, because the pipeline zero-fills raw and *then*
applies the frozen scaler, so raw 0 is not the origin:

```
zero-filled Group D, after the scaler:   mean 0.368 sigma, 0 of 30 dims past 2 sigma
real training rows farther from centre:  94.65%
```

The zero-fill is **inside** the training distribution — nearer the centre than 95%
of real rows. Off-domain text is not. A declared degradation beats a silent
distortion. Cost, which belongs in the paper: non-SSH protocols are classified on
**98 of 128 features**.

### Phase 2: a second honeypot, built and then deliberately not deployed

The Heralding parser works — 36 tests, timestamps handled (Heralding writes naive
UTC, and `fromisoformat` would have read it as local time and shifted every
session 5.5 hours, breaking peer attribution), one-line-per-session handled,
credentials mapped onto micro-states the taxonomy already has.

**MT3 cannot classify it.** Zero agreement on six scenarios, and confident:

```
scenario            rule label            MT3 said                conf  phase
bare connect        RECON_IP_SCAN         DISC_NETSTAT_SCAN      1.000      3
http brute force    ACCESS_BRUTE_HTTP     RECON_OS_DETECT        0.567      0
factory defaults    ACCESS_DEFAULT_CRED   EXEC_WGET_EXEC         0.985      2
```

A bare TCP connection with no login attempt comes back as a network scan at
**confidence 1.000**, which is phase 3 — enough to clear the auto-blacklist
threshold. Deploying it would have **blocked users for opening a TCP connection**.

Cause, measured: Heralding reports no bytes, packets, TCP flags, TLS or commands,
so **only 55 of 128 feature columns are non-zero** and the model is extrapolating.

So two things were built instead of a deployment:

1. **The trust gate** (`62bb614`) — keyed on the session's *source*, not its
   protocol, because a Cowrie telnet session is shell-shaped while a Heralding
   telnet session is credential-shaped. The verdict is still computed and logged
   for every source; it may only *act* for `cowrie_real`.
2. **A fine-tune** (`4984bfa`, `f362ab4`) — a separate model so the published
   comparison table still describes the model it was measured on, trained with
   replay so it could not improve on Heralding by forgetting Cowrie. It **fixed
   the safety problem** (bare connect → `RECON_IP_SCAN` phase 0) and did not
   regress `test_real` (0.8272 → 0.8284), with Heralding held-out macro-F1
   **0.8924** — but scored only **3/6** on the hand-built scenarios, so the gate
   stayed closed.

That gap is the lesson: 0.89 on held-out data that shares the generator's quirks
is not generalisation. The acceptance scenarios use 2-4 auth attempts while the
generator emits 3-40, so the model learned the generator's distribution rather
than the concept. **Widening the generator to pass its own exam was deliberately
not done**, because the resulting number would not be defensible.

### The mitigation branch merged

`f7810ee` — 9 commits, 60 files, +8,553 lines: the `response_mitigation` package
and `deploy/sandbox/`, the hardened internet-facing kit.

One conflict, six hunks, and one of them mattered: the branch sent every verdict
to the new engine **unconditionally**. Merged as written, that would have silently
undone the trust gate above and started blocking people again. The engine now
inherits it. The gate lives in the pipeline rather than the engine on purpose —
the engine's job is "given a verdict, act safely"; whether the verdict is worth
believing is upstream of that.

### The four security findings

All from the 2 November review (`02-11-2026 FINDINGS.md`, `HONEYPOT_AUDIT.md`
PART 3).

**API authentication** (`26a7e10`). `POST`/`DELETE` on the blacklist and
whitelist had no authentication and CORS allowed every origin, so anyone who could
reach port 5000 could whitelist themselves past the gateway, the honeypot and the
model in one request. Now a bearer token, narrowed origins, and — the part that
matters — **a start-up refusal** when a reachable address is bound with no token.
Two things found while wiring it: `run_pipeline.py` calls `app.run()` directly and
so bypassed the guard entirely (and it is what `live_demo.py` runs, so the guard
would have been missing from the only path anyone uses), and placed after
`startup()` it refused only after 90 seconds of model loading — now 0.4 s. The API
also defaults to `127.0.0.1` now; nothing outside ever needed port 5000.

**The whitelist bypass** (`a843de0`). `skip_reason()` never received the verdict,
so a whitelist short-circuited everything at any phase and any confidence — an
attacker who spent 70 minutes behaving became immune to detection, and the longer
they behaved the safer they got. A strong verdict (phase ≥ 2, confidence ≥ 0.90)
may now override a whitelist for **diversion to the honeypot**, never for a
**firewall drop**, because that can lock you out of your own server.

**The reputation scorer** (`838fcc4`). Every signal was an average over 20
sessions, so one serious session was worth 5% of the score. Now the worse of the
average and the worst single session in a 5-session window:

```
19 clean + 1 serious   0.166 -> 0.542   crosses the suspicious threshold, blocks promotion
20 clean   (floor)     0.179 -> 0.179   unchanged to six decimals
20 serious (ceiling)   0.654 -> 0.654   unchanged to six decimals
```

The short window is deliberate: over the full history a spike would be permanently
sticky and the promoter could never rehabilitate anything.

**Benign sessions — finding #1, the Critical one** (`828ec08`). **Mitigated, not
closed.** MT3 is a closed-set classifier over 45 *attack* labels, so a benign
session cannot come back "safe" and four real benign SSH sessions were all
labelled attacks, one auto-blacklisted.

Abstention was tried first and ruled out by measurement:

```
                   benign sessions     real attacks
confidence           0.301 - 0.995     0.637 - 0.828
top1-top2 margin     0.087 - 0.992     0.421 - 0.698
mahalanobis dist     425   - 553       424   - 642
```

Benign reaches **higher** confidence than any attack, so no threshold exists. The
fix is corroboration instead: MT3 may not block while the gateway's connect-time
classifier *independently* called the source benign. The gateway has a benign
verdict; MT3 structurally cannot, so this borrows the capability rather than
faking it.

I got the independence check wrong once and **44 tests caught it.** A *re-derived*
verdict is not an observation — measured, the cron-backdoor attack re-derives to
`BENIGN 0.14 []`, *identical* to a harmless admin session, while a benign
`systemctl reload nginx` re-derives to `SUSPICIOUS`. Corroborating with that
suppressed real attacks and still failed to protect benign users.

### Phase 0 readiness

The deployment kit was audited before anyone uses it. Worst find: **it never set
`PIPELINE_SOURCE`**, so every real capture on a public server would have been
filed `"unspecified"` — unrecoverably indistinguishable from months of simulated
traffic. Also two of the kit's own tests were broken, one because the write

## 4. The biggest finding, which came out of a side measurement

Measuring Mahalanobis distance for the abstention attempt produced something more
important than the attempt itself:

```
X_train rows            p50   5.5    p95  15.4
held-out test_real      p50   3.5    p95   7.4     <- inside, so the measure is sound
LIVE Cowrie sessions          425 - 642
```

**A session produced by the running pipeline is roughly 75x further from the
training distribution than the held-out test data is.** Both benign and hostile
live sessions sit out there, so it cannot be used to tell them apart — but it says
plainly that **the published 0.8187 macro-F1 describes data that does not resemble
what the live system actually feeds the model.**

One mechanism explains both finding #1 and the Heralding failure: a closed-set
classifier being asked about inputs unlike anything it trained on. This belongs in
the paper as a threat to validity, separately from the synthetic-data provenance
issue already recorded in `DECISIONS.md`.

Every result line now carries `ood_distance` and `ood_p95_train` so it is visible
per session. It is an **honesty signal, not a gate** — gating on it would suppress
every live verdict, including real attacks.

## 5. Mistakes made and corrected, for the record

Kept because each one cost time and would cost it again:

- **Corroborating with a re-derived verdict** — suppressed real attacks, 44 tests
  caught it.
- **`ood_distance` called `self.mt3.scale()`**, which a stubbed MT3 does not have.
  Every session became a logged exception and the sandbox recorder dropped to 0
  processed sessions. It is reported and never relied on, so it is now computed
  defensively.
- **A scorer test asserted the wrong thing.** I claimed the score should be
  identical regardless of clean-history length; it rises slightly at 40 clean
  sessions because the frequency signal counts total connections — the *opposite*
  of the harm. The code was right and the assertion was wrong.
- **A measurement understated its own result.** `Session.close()` recomputes
  entropy from `payload_snip`, so setting it beforehand is silently discarded.
  That reported the scorer fix as +0.211 instead of +0.376.
- **Scope creep, caught and reverted.** A draft of the whitelist fix also extended
  `never_block` to diversion. Those were designed DENY-only and a test asserts it,
  so that went beyond what the finding recommended.
- **Three generator/labeller drifts**, each caught by the generator's own
  verification rather than by a human reading output — including one that exposed
  a real flaw in my labeller (one username with an empty password is a
  passwordless default, not account enumeration; you cannot enumerate with one
  probe).
