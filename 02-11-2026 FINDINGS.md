## 1. Can MT3 classify a safe sequence?

> *"If the whitelists never go through MT3 then how will MT3 know how to classify a safe sequence?
> Is my MT3 only trained to identify an attack among the 45 states? Isn't that a flaw if a model
> can't identify a safe sequence?"*

### What was checked

`configs/schema.py` (the full label list), `honeypot_dataset/notebooks/01_process_real_data.ipynb`
(how the real datasets were labelled), `traffic_gateway/feature_bridge.py` and
`ml_analytics/mt3_pipeline/` (any abstention or out-of-distribution handling), and then the trained
model itself.

### What was found

**All 45 labels are attack micro-states.** `RECON_*`, `ACCESS_*`, `EXEC_*`, `DISC_*`, `PRIVESC_*`,
`PERSIST_*`, `EVASION_*`, `LATERAL_*`, `EXFIL_*`. There is no benign class, no "normal", no "none
of the above".

MT3 is therefore a **closed-set classifier**. Its softmax over 45 attack classes sums to 1, so any
input — benign, malformed, or nothing at all — must come back as a probability distribution over
attacks. It is structurally incapable of outputting "safe". There is no abstention, reject, or
out-of-distribution mechanism anywhere in the inference code.

**Real benign data existed and was deliberately discarded.** From notebook 01:

```python
"BENIGN": None,   # skip benign traffic
"Normal": None,   # skip benign traffic
```

CIC-IDS2017 is roughly 80% BENIGN; UNSW-NB15 has a large Normal class. Per `DECISIONS.md` these two
datasets are the *only* genuinely real data in the project — and the benign half was dropped.

### The measurement — real Cowrie sessions, real features

Genuinely benign SSH sessions were driven through the gateway into the live Cowrie container, so
every feature was extracted from a real captured session. Classified by
`ml_analytics/artifacts/mt3_full_d256/best.pt` (3,759,510 params, val macro-F1 0.9599):

| Benign session | Gateway heuristic | MT3 verdict | Confidence | Phase |
|---|---|---|---|---|
| `whoami ; uptime ; ls ; exit` | **BENIGN (0.14)** | `EXEC_MEMFD_EXEC` (fileless malware) | 0.717 | 2 |
| `df -h ; free -m ; exit` | MALICIOUS (1.0)\* | `DISC_PROC_ENUM` | 0.915 | 3 |
| `cd /etc ; cat nginx.conf ; systemctl reload nginx ; exit` | MALICIOUS (1.0)\* | `PERSIST_SYSTEMD_SVC` (backdoor install) | 0.898 | 5 |
| logged in, typed nothing | MALICIOUS (1.0)\* | `ACCESS_BRUTE_SSH` | 0.640 | 1 |

\* *see the feedback loop below — these scores are an artefact of the first session's blacklisting.*

**Every one of them is an attack label above the action threshold.** The first session was
auto-blacklisted on the spot:

```
[IP_BLACKLISTED] ip=127.0.0.1 reason=MT3: EXEC_MEMFD_EXEC (phase 2 Execution, conf 0.72)
                 source=mt3_pipeline risk_score=0.7174
response_mitigation.gateway: auto-blacklisted 127.0.0.1
```

The honeypot also escalated its own interaction level in response — low → medium on
`EXEC_MEMFD_EXEC`, then medium → high on `PERSIST_SYSTEMD_SVC`, planting `/etc/shadow` and a fake
SSH host key to bait an "attacker" who was running `cat nginx.conf`.

### Correction to an earlier claim

An initial probe using hand-built records reported `EXEC_WGET_EXEC` at **0.982** for a *completely
empty* session. **That did not reproduce on real traffic, and the claim should not be used.** A
genuinely empty connection never emits `cowrie.session.closed`, and the pipeline only processes
closed sessions — so it never reaches MT3 at all. Verified: the bare-connect session appears in
`cowrie.json` with only `session.connect` and `client.version`, and no result row.

The realistic minimum-evidence case is **"logged in, typed nothing"**, which does reach MT3 and
comes back `ACCESS_BRUTE_SSH` at 0.640 — still above the 0.5 floor, still blacklisted. Less
dramatic, equally wrong.

Otherwise the hand-built probe was directionally accurate: it predicted the same four classes with
confidences within ±0.1 of the real-feature run (0.602→0.717, 0.912→0.915, 0.981→0.898,
0.835→0.640).

### The feedback loop — a second finding from the same run

Look at the first two rows again. On the only session where the gateway's heuristic had a clean read,
**the heuristic was right and MT3 was wrong**: heuristic said BENIGN at 0.14, MT3 said
`EXEC_MEMFD_EXEC` at 0.717, and MT3's answer is the one that became durable state.

It then poisoned everything after it. Once `127.0.0.1` was blacklisted, the gateway's own verdict for
every later session from that IP was `MALICIOUS` at score **1.0** with `signals=['blacklist']` — the
blacklist *is* the signal. So one MT3 false positive silently rewrites the gateway's assessment of
all subsequent traffic from that source, and nothing in the record distinguishes "scored malicious on
its own evidence" from "scored malicious because we already blacklisted it".

This matters beyond the false positive: `gateway_score`, `gateway_verdict` and `gateway_signals` are
written into every row of `pipeline_results.jsonl`, which is the file the dashboard reads and the
file any later analysis would use. Those columns are **not independent** of MT3's earlier decisions
on the same IP, and must not be treated as a second opinion in any evaluation.

### Why the usual defence does not apply

The standard answer is that a honeypot has no legitimate users, so everything reaching it is hostile
by definition and no benign class is needed.

**That does not hold for this architecture.** Under zero-trust routing every `UNKNOWN` IP is sent to
the honeypot, including every legitimate first-time user. And because the promoter only reviews
`BLACKLISTED` records (finding 3), a legitimate user *must* pass through the honeypot and be flagged
before they can ever reach the real server. The design actively routes legitimate traffic into MT3.

### Why it matters for the paper

`test_real` holds 21 attack classes and no benign data. So the headline **macro-F1 of 0.8187 says
nothing about the false-positive rate on legitimate traffic** — that number has never been measured,
because there is nothing in the test set to measure it against. A reviewer will ask.

It also means `response_mitigation/replay.py`, which reports TP / FP / FN / TN given labels, has no
benign-labelled sessions to work with. The tooling for the false-positive rate exists; the data does
not.

### What to do

1. **Keep the benign rows and add a benign class.** ROADMAP M2 already requires rebuilding the
   splits to remove the 29.74% leakage — do both in one pass rather than retraining twice. Even two
   classes (`BENIGN_FLOW`, `BENIGN_SHELL`) would change the model's character.
2. **Add abstention without retraining.** Max-softmax is useless here, but an energy score or
   Mahalanobis distance on the penultimate layer needs only one pass over the training set to fit.
   Below threshold → OBSERVE, never DIVERT.
3. **Cheap guard available today** in `response_mitigation/policy.py`: refuse to DIVERT on a
   session with **no commands at all**. The real run shows why the bar has to be commands, not
   logins: "logged in, typed nothing" had one login, zero commands, and was still labelled
   `ACCESS_BRUTE_SSH` at 0.640. A few lines of code.
4. **Record it in `DECISIONS.md`**, alongside "MT3 has no CRF despite the naming". Same category:
   a gap between what the naming implies and what the model does.

## 2. What if someone is whitelisted and then attacks?

> *"What if I pretend to be a whitelist and then run an attack? Would I still be blacklisted?"*

### What was found

Probably not. The chain, with every link confirmed in code:

```
POST /api/whitelist   →  no authentication, CORS(app) wide open
      ↓
you are WHITELISTED
      ↓
traffic_router sends you to the REAL SERVER, not the honeypot
      ↓
safelist.py checks is_whitelisted BEFORE the DIVERT/DENY split,
so every MT3 verdict returns "skipped: whitelisted" at any phase or confidence
      ↓
only the heuristic scorer can re-blacklist — and it averages
over up to 50 sessions (session_tracker.MAX_HISTORY_PER_IP)
```

**Anyone who can reach port 5000 gets past the gateway, the honeypot and MT3 in one HTTP request.**
`traffic_gateway/api.py` on `main` has `CORS(app)` and no login on four state-changing endpoints:
`POST` and `DELETE` on `/api/blacklist` and `/api/whitelist`.

Even a legitimately earned whitelist is nearly as good. An attack from a whitelisted IP *is* fully
classified by MT3 and written to the results file — but the mitigation layer records
`divert / skipped: whitelisted` and takes no action. The only remaining backstop is the heuristic
score, and every one of its signals is an **average**: `avg_entropy`, `avg_bytes_in`,
`avg_duration`, honeypot ratio. One attack among 49 clean sessions barely moves it. A whitelisted IP
by definition has a long clean history, because it spent 70+ minutes earning one.

**The longer an attacker behaves, the harder they become to catch.** `traffic_gateway/data/ip_records.json`
already shows `sample=20 sessions` diluting a score to 0.136.

On spoofing specifically: SSH requires a full TCP handshake, so blind IP spoofing fails. But the
gateway's only identity check is the source address, so ARP-spoofing onto a whitelisted LAN address
would work.

### What to do

1. **Commit the dashboard authentication before anything faces the internet.** The work already
   exists, uncommitted, on the teammate's machine. This is more urgent than any item on the
   mitigation-layer improvement list.
2. **Let MT3 override the whitelist above some phase** — invert the order in
   `safelist.skip_reason()` so a high-phase, high-confidence verdict wins over `is_whitelisted`.
3. **Make the heuristic use a recent-window maximum, not a lifetime average**, so one serious
   session cannot be diluted away.

## 3. How long before an IP can reach the real server?

> *"When I first enter the pipeline do I enter the honeypot by default? Is it only after the MT3
> model classifies that I'm whitelisted? How long does an IP stay in the honeypot before it can
> actually access the real server?"*

### What was found

**Yes, you start in the honeypot.** Status `UNKNOWN` → honeypot, reason
`unknown_zero_trust_redirect`. The one exception is `GATEWAY_CLASSIFIER_ROUTING=1` with a BENIGN
verdict, which reaches the real server on the first connection.

**No, MT3 does not whitelist you. MT3 can never whitelist anything.** It only ever contributes a
*blacklist*, through the mitigation layer's DIVERT. There are exactly two ways to become
whitelisted: the promoter loop, and the unauthenticated `POST /api/whitelist`.

**How long — this is the paradox:**

| Your path | Time to the real server |
|---|---|
| Behave well, never get flagged | **Never.** The promoter only reviews `BLACKLISTED` and `PROBATION` records. An `UNKNOWN` IP is never reviewed. |
| Get blacklisted first | **70 minutes minimum** |

The 70 minutes is `MIN_BLACKLIST_SEC` (600 s) + `PROBATION_SEC` (3600 s), on a 60 s review loop,
and also requires a score below `SCORE_PROMOTE` (0.25) at review and fewer than 3 strikes during
probation.

**Measured:** `ip_records.json` records `127.0.0.1` blacklisted at 11:05:53 as
`"MT3: ACCESS_BRUTE_SSH (phase 1 Initial Access, conf 0.88)"`, promoted to probation at 11:15:59,
and `fully_whitelisted_at` 12:16:41 — **70 minutes 48 seconds** from MT3-flagged attacker to full
access to the real server.

**So being flagged as an attacker is the only automatic route to trusted access.** That is almost
certainly not the intended design.

### The full lifecycle

| Transition | Condition | Time |
|---|---|---|
| `UNKNOWN` → `SUSPICIOUS` | heuristic score ≥ 0.45 | after a session |
| `UNKNOWN` / `SUSPICIOUS` → `BLACKLISTED` | heuristic score ≥ 0.70, **or** MT3 via DIVERT | after a session |
| `BLACKLISTED` → review eligible | `MIN_BLACKLIST_SEC` | 600 s |
| `BLACKLISTED` → `PROBATION` | score < 0.25 | 60 s review loop |
| `PROBATION` → `WHITELISTED` | `PROBATION_SEC` clean, < 3 strikes | 3600 s |
| `WHITELISTED` → `BLACKLISTED` | heuristic score ≥ 0.70 (continuous monitoring) | after a session |

## 4. Is the gateway only tracking lists, rather than classifying?

> *"So basically the only functionality of the traffic gateway is to keep track of the blacklist and
> whitelist, with the promotion and all the associated things with it, instead of classifying the
> network flow as malicious and non-malicious?"*

### What was found

**For routing, essentially yes.** `CLASSIFIER_ROUTING` defaults to off
(`bool(os.getenv("GATEWAY_CLASSIFIER_ROUTING", ""))` → `False`). With it off, destination is decided
purely by IP status: `WHITELISTED` → real server, everything else → honeypot. The content of the
traffic does not change where it goes. `traffic_classifier` still runs on every connection, but its
verdict is **telemetry only** — stored as `gateway_score` / `gateway_verdict` / `gateway_signals`.
The router's own comment says it: *"telemetry always; routing when enabled."*

**But the classifier does control *status*, which controls routing next time.** After each session,
`inspection_gateway._post_session()` re-scores the IP and escalates on its own:

| Current status | Score ≥ 0.45 | Score ≥ 0.70 |
|---|---|---|
| `UNKNOWN` | → SUSPICIOUS | → BLACKLISTED |
| `SUSPICIOUS` | — | → BLACKLISTED |
| `WHITELISTED` | warning logged | → re-BLACKLISTED |

So it classifies; the classification just writes the status, and routing reads that status on the
next connection. Indirect and one session behind, rather than inline.

### Two classifiers, easily confused

| | Heuristic scorer | MT3 |
|---|---|---|
| Runs | At connection time, and after each session | After each session closes |
| What it is | 5 hand-weighted behavioural signals | 128 features, 45 micro-states, trained |
| Controls | Routing and IP status | Honeypot adaptation and mitigation |

**MT3 never touches routing directly.** It influences it only through the blacklist the mitigation
layer writes — and the heuristic can undo that blacklist 70 minutes later. The trained model is
subordinate to a hand-weighted formula. This is worth fixing before the A/B study, because it means
the adaptive arm's own classifier can be overruled by a heuristic.

### The gateway's seven actual jobs

Only the last is list-keeping:

1. It is the TCP proxy — it moves the bytes
2. **It is the only source of real attacker IPs for the whole pipeline** (`resolve_peer_ip` reads
   the gateway log; without it, attribution is impossible)
3. Segregation — honeypot vs real server
4. Rate limiting, including the 100/min trusted bucket
5. Connection-time classification (telemetry by default, control if enabled)
6. Post-session reputation scoring → status escalation
7. Blacklist / whitelist state and the promotion lifecycle

## 5. Does "blacklisted" mean the IP is blocked?

> *"Does blacklist necessarily mean blocking that IP from accessing the real server again?"*

### What was found

**No, on both counts.**

**Blacklist is not a block.** `traffic_router.py:13` routes a blacklisted IP **to the honeypot**,
reason `blacklisted_honeypot_observation`. They still connect, still get a shell, still get logged.
The only action that actually drops traffic is DENY (nftables), which is off by default
(`MITIGATION_FIREWALL=0`) and cannot run on Windows at all.

**And it is not permanent.** The promoter rehabilitates automatically — see finding 3. Blacklisting
is a temporary, self-reversing state, not an exclusion.

A subtlety worth noting: blacklisting does not actually change where an `UNKNOWN` IP goes, since
both go to the honeypot. What it changes is that the IP becomes *eligible for promotion*, which an
`UNKNOWN` IP never is.

## 6. Does a blacklisted IP re-run the whole pipeline?

> *"Does a blacklisted IP go through the entire pipeline only to be mitigated again?"*

### What was found

**Yes — and it is correct.** Measured during the verification run: three sessions returned
`divert / skipped: already blacklisted`, and each had first gone through the complete chain —
128-feature extraction including the DistilBERT encode, MT3 inference, and the configurator.

Nothing short-circuits on "already blacklisted". The check lives in `GatewayExecutor.skip_reason()`,
the last step, after the policy, the safelist and the mode gate.

**No change needed.** The expensive work is not wasted:

- the classification *is* the product — it is the intelligence being collected
- the honeypot reconfiguration depends on each fresh verdict (this is how `EVASION_LOG_WIPE`
  escalated interaction to high and planted `/etc/shadow`)
- the A/B study's "kill-chain depth reached" metric needs every session classified

The only genuinely repeated work is the DIVERT no-op, which is a dictionary lookup. Worth
understanding, though: **per-session cost does not drop once an IP is known.**

Related: once an IP is DENY'd at the firewall it stops connecting entirely, so it produces no
further sessions and no further intelligence — which is the yield problem flagged against enforce
mode in `HONEYPOT_AUDIT.md`.
